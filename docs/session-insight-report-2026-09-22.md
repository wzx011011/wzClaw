> 3654 条用户提示，去噪后约 1513 条，980 个 turn 有完整耗时指标，合计约 12,884 次
> 模型请求，覆盖 09-12～09-22 v3 大脑网络全程）＋ `~/.zcode/v2/sessions/` 早期库
> （4—5 月 v1 时代约 80 个会话）。抽样精读 9 个主力会话完整提示序列。

## 总账

- 9% 的提示在发起 review（140 条），11% 的模型请求花在这里
- 6% 是「继续/开工」类续跑燃料（96 条），却烧掉 17% 的模型请求
- 4% 是纠正返工（62 条，约 724 次请求）
- 13 条连接排障提示烧掉 342+ 次请求
- **每 10 次请求约有 1 次花在补返工和排环境故障上——这就是效率提升空间的主体**

## 一、回头看：哪些命令和提示真正有效（按实测效果排序）

### 1. 「/goal + 验收边界 + 决策上问」——最值钱的单条提示

- `/goal review一下当前代码，有问题就修复。然后再做review修复，直到没有问题为止`
  （167 次请求、110 分钟一气呵成，09-22）
- `/goal 完成剩下的工作，需要决策的以提问的方式问我`（09-20）——长自主跑里最大的
  风险是代理自行拍板，加这句后返工明显减少
- 对照：单纯「继续」也曾一次跑 277 次请求，但目标模糊，跑完后追问「为什么还有
  没修复甚至没动的」——**带验收边界的 /goal 比裸「继续」产出密度高得多**

### 2. 「先探明再实现」链式提示——协议工作的正确姿势

09-21 原话：`能不能探测一下zcode到子Agent的逻辑到底是怎么做的，我们跟他的一样吗;
清楚之后做一下对齐;再看看还有哪些功能我们是不完全确定的，全部都探测一下zcode的
具体实现，做一下对齐修改，最后提交代码，确保ci通过`——探针→对齐→兜底探测→实现
→CI 一条龙，43 次请求完成。AGENTS.md 设计原则第 1 条「协议字段以实测为准」就是
被这类摸索逼出来的。**探测式提示是项目里 ROI 最高的一类**。

### 3. 「Mockup 先行」——UI 工作的转折点

09-18 发明的流程：`要不你先用网页画出来你的理解的要还原的样子，然后我同意了再开工`
→ 批复 `这个效果非常好 就按照这个效果严格实现`。批准后的实现只花 17 次请求；此前
裸描述 UI（`参考网页版ui 把所有没实现的都实现`，32 次请求）引来连续多轮「这个布局
也很有问题啊」。纯文本里画 ASCII 回合块草图也很有效，比文字描述歧义少一个量级。

### 4. 「实证与反妥协」纠偏语——设计原则的源头

- `都不要瞎猜，不确定的都去看看zcode到底是怎么做的`（09-21）
- `推断的能不能实锤`（09-22）
- `不要用妥协的方案 从本质上修复`、`等等 这个去重的逻辑不对吧，不是从根本解决问题`

每次出现都直接改变代理行为方向，后来全部固化进 AGENTS.md 原则 1/2/4。成本极低
（14 条提示共 322 次请求），杠杆极大。

### 5. 「一句话规则沉淀」——全库最便宜的操作

`把这个规则写入md文档`、`以后都放到这个目录 规则写入md`、`以后构建要加小版本号
不然都不知道是否最新版本`、`架构里面 ui不管新旧，以后不要再叫旧ui了`——13 条提示
只花 27 次请求，产出了 APK 发布纪律、UI/协议分层表述纪律等所有长期规则。
**发现教训当场一句话入档，是性价比最高的动作**。

### 6. 「侧会话规划 → 主会话执行」的接力棒

`请按侧会话的"复审后终态修复计划"执行：先 relay v2 per-probe 路由和 x/* 数值错误码，
再 Android 单栈迁移与移除假成功 UI，随后 desktop/companion 韧性，最后补 CI 门禁；
不要构建 APK。`——带序号计划粘进主会话 + 明确「不要做什么」，102 次请求跑完全程。

### 7. 直接粘贴原始报错

QR 码栈溢出完整堆栈、`{"detail":[...]}` JSON——贴原始错误输出的定位都只要几步。
比转述快得多：裸发「报错了」曾烧 72 次请求（代理要自己找现场）。

### 8. 批量问题清单 + 统一根因定位（09-22 已进化出的终态）

`我说几个我发现的问题吧：子输出混了、agent和目标没显示、明明已停止还在进行中……
把我发现的问题统一重新审查和根因定位一下……我不想反反复复的修改了；先确定问题
根因，我同意之后再开始修复`——一条提示列全 6 个症状 + 显式分阶段（根因→批准→修复）。
随后 `好 那就全部解决掉，一定要彻底。不要妥协方案` 一口气 219 次请求完成修复。
**这是全部 1513 条提示里最成熟的一条工作流**。

### 9. 面向架构的隐喻式提案

v3 转折点：`把appserver的实现抽象出来，做成独立自洽的手和大脑，手机端就是一个远程
控制的ui手机端而已`——先给隐喻再让代理补细节，比让代理自由发挥架构靠谱得多。

## 二、造成返工/浪费的模式（重来要规避）

1. **时间与指代词含糊——最大单点浪费源**：`完全恢复之前手机端的ui`（「之前」歧义，
   连发三条澄清 + 追问「为什么理解错了」）；`新建会话的时候…`（指代页面 vs 创建后，
   同一问题 4 种问法）；`底部弹窗`（错误 toast vs 底部抽屉，3 个来回）。
   **规律：含「之前/刚才/那个/上面」相对指代的提示出事概率极高，要给锚点**。
2. **一揽子模糊大请求**：`用官方手机端方案`（跑偏成网页端）、`把所有没实现的都实现`
   （必然漏）。对照：拆成编号清单逐条验收。
3. **UI 逐条微调循环**：几十条 5—20 次请求的小修提示。效率杠杆不在改得快，
   而在批准一张稿子后批量施工。
4. **环境故障反复现场排查**：连接类 13 条烧 342+ 次，根因是 frpc/SNI 外部问题，
   沉淀后一行「`docker restart frpc` 即愈」。**环境类故障第二次出现就该写文档**。
5. **并行会话互踩**：`是不是另一个会话有新的改动`（连问 3 次）。应固定单写者纪律。
6. **v1 时代最大成本（4—5 月）**：两个月逐系统复刻 Claude Code，9 月换芯全部被
   官方 app-server 取代。**引擎不是差异化所在，relay/配对/手机端 UI 才是**。
7. **安全瑕疵**：会话里两次把 NAS 密码直接贴进聊天，违反原则 6（凭据不进聊天输出）。

## 三、如果重新开发：提示词效率手册

### 阶段 0 · 立项（一次写清）

```
技术选型先回答一个问题再开工：哪些层直接采用现成引擎（不自己造），
哪些层是我们自研的差异化（relay/配对/UI）。
给出：架构隐喻一句话 + 3 条不变量 + 明确的非目标清单。
选定后写入 AGENTS.md，后续所有会话以它为准。
```

### 阶段 1 · 协议/对接类任务（探针先行）

```
先跑探针把 <接口> 的真实 schema 钉死，结果追加进 APP-SERVER.md（含畸形应答实验），
我不确认前不写实现代码。探测与实现分两步，中间停下来给我看结论。
```

### 阶段 2 · UI 类任务（稿子先行）

```
先用网页 mockup 还原你理解的 <页面/交互>，附一张与参照截图的差异清单（逐条编号）。
我批准哪几条，你就只实现那几条。禁止在未批准的稿子上直接改 Flutter 代码。
```

### 阶段 3 · 长任务执行（/goal 三件套）

```
/goal 按 <文档/侧会话> 的编号计划执行：先 A 再 B 最后 C。
验收标准：<测试全绿/CI 通过/真机可跑>。
过程中需要拍板的一律以提问方式问我，不要自行决定；
禁止用妥协方案达成目标，做不到就显式报「暂不支持」。
```

### 阶段 4 · 缺陷修复（根因门控）

```
以下是我发现的 N 个症状：<编号清单>。
先统一做根因定位，给每个症状标注：根因/推断/未知，推断必须给证据（源码行号或实验）。
我确认根因后才开始修。修复必须从机制上解决，禁止去重/打补丁式遮盖。
```

### 阶段 5 · Review 循环

```
/goal 按 AGENTS.md 设计原则与编码规则逐条 review 当前改动，
有问题就修，修完再 review，直到零问题为止。每个拒绝/修理由带规则名。
```

### 教训沉淀（随时）

```
以后 <规则一句话>。把这条追加进 AGENTS.md 对应小节。
```

### 会话卫生三条（新规则，AGENTS.md 尚未收录，建议补）

1. **单写者**：同一仓库同一时刻只有一个会话持写权，侧会话/并行会话只读或只出计划；
   开工前代理应先 `git status` 声明工作树归属。
2. **环境故障二次入档**：任何环境类故障（连不上/构建产物损坏/模型拉不到）第二次
   出现时，先查 AGENTS.md 已知故障表，修完追加一行「症状→根因→一条命令解法」。
3. **锚点纪律**：提示里出现「之前/刚才/那个」时主动补锚点（文件名/截图/commit/
   页面名）；代理遇到无锚点的相对指代应当先反问而不是猜。

## 四、一句话总结

被反复验证的效率公式：**探针/稿子先行钉死事实 → /goal 带验收边界的长自主跑 →
根因门控的修复 → 一句话规则沉淀**。09-22 那天的提示（6 症状清单 + 根因门控 +
219 次请求一杆清）就是这个公式的完全体。重开发时从第一天按这个风格发提示，
粗估可省 10%—15% 总请求量（返工 + 重复排障 + UI 微调循环三块），
并归零 v1 时代「造引擎两个月」这类方向性浪费。
